第1章へ：チャットとエージェントは何が違う？

Chapter 01

チャットとエージェントは、
何が違う？

この章がこのガイドでいちばん大事です。ここさえ腹落ちすれば、あとの章はすべて「その応用」になります。

3行でいうと

  • ChatGPT（チャット）は、教えてくれる人。
  • Codex（エージェント）は、やってくれる人。
  • だから、Codexには「聞く」のではなく「頼む」。

🍳 たとえるなら

あなたがカレーを作りたいとします。

ChatGPT（チャット）は、料理上手な友達です。「玉ねぎは飴色になるまで炒めてね」とレシピを教えてくれます。でも、鍋を振るのはあなたです。

Codex（エージェント）は、キッチンに入ってくれる助手です。「冷蔵庫のもので夕飯を作っておいて」と頼むと、実際に冷蔵庫を開け、材料を切り、火にかけ、できあがりを見せてくれます。

※ ただし、勝手に全部やるわけではありません。「この包丁を使っていい？」「この材料は捨てていい？」と、要所であなたに確認を取ります。この確認のことを、あとの章で「承認」と呼びます。

具体的に、何が違うのか

　ChatGPT（チャット）Codex（エージェント）
返ってくるもの文章・答え・アイデア実際の作業結果（ファイルの変更）
手を動かすのはあなたCodex
あなたのPCのファイル基本は触らない読む・書く・作る・消す（許可した範囲で）
かかる時間数秒〜数十秒数分〜数十分（長い仕事もこなす）
依頼の言い方「〇〇って何？」「〇〇をやっておいて」
途中の確認基本なし要所であなたに承認を求める
向いている用途調べる・考える・書く作る・直す・整える・繰り返す

「AIエージェント」の3つの条件

世の中で「AIエージェント」と呼ばれるものは、だいたい次の3つを持っています。Codexも例外ではありません。

1 / 3

道具が使える

ファイルを開く、検索する、プログラムを走らせる、ブラウザを見る。手足がある、ということです。

2 / 3

自分で段取りを決める

「まず調べて、次にこう直して、最後に確認する」という手順を、自分で組み立てます。

3 / 3

結果を見て、やり直す

やってみて失敗したら、原因を見て別の方法を試します。1回で終わりません。

この3つがあるから、エージェントは「1往復の会話」では終わらない仕事ができます。逆にいうと、時間がかかるのも、途中で確認してくるのも、この性質のためです。

Codexは何が得意で、何が苦手か

正直に書きます。ここを誤解すると「思ったのと違う」になります。

得意

  • 手順がはっきりしている、面倒な繰り返し作業
  • たくさんのファイルを横断して調べる・直す
  • 「動くかどうか」を実際に試して確かめる
  • 下書きを一気に作る（0→1）

苦手・要注意

  • あいまいな指示（「いい感じにして」）
  • あなたの頭の中にしかない前提の推測
  • 取り返しのつかない操作を任せること
  • 長時間の作業での「うっかり忘れ」（第7章で解説）
深掘りプログラミングをしない人にも意味があるの？

あります。ただし正直に言うと、Codexは「開発作業」を主な想定として作られたエージェントです。ここをごまかすと、あとで「聞いてた話と違う」となります。

そのうえで、非エンジニアにとっての価値は3つあります。

  • 資料まわりの自動化。PDF・スプレッドシート・文書ファイルを扱う公式スキル（第8章）が用意されており、「フォルダ内の資料を読んで一覧表にする」といった作業を任せられます。
  • 作りたいものが作れる。簡単なツールやWebページを、あなたが書けなくても形にできます。
  • エージェントの考え方が身につく。この考え方は、これから出てくる他のAIエージェントにもそのまま通用します。Codexで覚えた概念は、ほぼ全部使い回せます。
深掘りなぜ「エージェント」という言葉なのか

agent は英語で「代理人」です。不動産の agent（仲介業者）や、スポーツ選手の agent と同じ単語です。

つまり「あなたの代わりに、あなたの目的のために動く存在」という意味合いです。「道具」ではなく「代理人」と呼ばれているのがポイントで、だからこそどこまで任せるかを、あなたが決める必要があるのです。第11章の「安全に使うコツ」は、この言葉の意味そのものです。

ここだけ覚えて

  • チャットは「教えてくれる」、エージェントは「やってくれる」。
  • だからCodexへの依頼は、質問文ではなく「お願いの文」で書く。
  • 手を動かす相手なので、どこまで許すかは自分で決める。これが全体を通じたテーマです。

Chapter 02

インストールと、
最初の起動

ここでいちばん多い勘違いを、先に潰しておきます。いま「Codexアプリ」を探しても見つかりません。

3行でいうと

  • 入れるのは ChatGPTデスクトップアプリ。いまは Codex 専用アプリはありません。
  • 起動したら、左上のモード切替で「Codex」を選ぶ。
  • これだけです。難しい設定は、後からで大丈夫。

🚪 たとえるなら

Codexは「別の建物」ではなく、同じ建物の中にある別の部屋です。ChatGPTという建物に入って、受付（左上の切替）で「Codexの部屋へ」と言う。それだけの話です。

2026年7月のアップデートで、ふつうのチャット・Work（仕事用の資料やツールとつなぐモード）・Codex の3つが、この1つの建物にまとめられました。このガイドで使うのはCodexの部屋だけです。だから、新しくインストールするものは何もありません——すでにChatGPTアプリを使っている人なら。

※ 2026年7月8日までは、単独の「Codexアプリ」が実在しました。いま単独アプリが入っている方は、ChatGPTデスクトップアプリに移行してください。

手順

  1. ChatGPTデスクトップアプリを入手する

    chatgpt.com/download から、Mac版・Windows版・Linux版をダウンロードします。すでに入っている人は、最新版に更新するだけでOKです。

    Macは .dmg を開いてアプリをアプリケーションフォルダへドラッグ。Windowsは .exe を実行するだけです。
    更新は、アプリのメニューから「ChatGPTについて」または「アップデートを確認」を選びます。分からなければ、上のリンクから最新版を入れ直せば同じことです。

  2. いつものアカウントでサインインする

    普段ブラウザで使っているChatGPTのアカウントと同じものを使います。新しく作る必要はありません。

  3. 左上のモード切替から「Codex」を選ぶ

    サイドバーのいちばん上に、いま何のモードかが出ています（「Codex ⌄」のような表示）。ここをクリックすると切り替えのメニューが開くので、Codex を選びます。以前のようにタブが常時並んでいるのではなく、切替式です。

    見つからないときは、次の順に探してください。
    ・サイドバー最上部の文字（アプリ名やモード名）をクリックしてみる
    ・サイドバーが隠れている場合は、左上のパネル切り替えアイコンで表示する
    ・設定（歯車マーク）の中に「Codex」の項目がないか見る
    それでも「Codex」が出てこない場合は、アプリが最新版でないか、お使いのプランや地域ではまだ順次公開の途中である可能性があります。アプリを最新に更新して、再度確認してください。

  4. 作業したいフォルダを選ぶ

    Codexの画面にある「フォルダを開く」「作業フォルダを選択」といった項目から選びます（表示名は版によって異なります）。見つからないときは、Finder／エクスプローラーからフォルダをCodexの画面にドラッグしても構いません。

    ここで選んだフォルダが、Codexの作業場になります。その外のファイルには、勝手には手を出しません——必要なときは必ずあなたに確認を求めます（第1章で触れた「承認」です。第3章で詳しく説明します）。

!

最初に選ぶフォルダは、慎重に。いきなり大事な仕事のフォルダを選ばないでください。おすすめは、次の手順で作る練習用フォルダです。

1. デスクトップに「codex練習」という名前のフォルダを作る
2. 手元にある、なくなっても困らない資料を3〜5個コピーして入れる
　（議事録のメモ、PDF、テキストファイルなど何でも構いません）
3. このフォルダをCodexの作業場に選ぶ

※ 中身が空だと、次の章の最初の依頼で「何もありません」としか返ってきません。必ず何かファイルを入れておいてください。第11章で詳しく説明しますが、この一手間が最大の安全策です。

深掘りMacで「画面収録」「アクセシビリティ」の許可を求められたら

ChatGPTアプリには、開いている画面の内容を見たり、他アプリと連携したりする機能があります。そのためmacOSが「画面収録」「アクセシビリティ」の権限を求めることがあります。

これはmacOSの標準的な確認で、アプリを使ううえで一般的なものです。ただし権限は「後から設定でオフにできる」ことを覚えておいてください。不安なら最初は許可せず、必要になった機能を使うときに許可すれば十分です。

場所：システム設定 → プライバシーとセキュリティ → 画面収録 ／ アクセシビリティ

深掘りWindowsで使う場合の補足（WSL2）

Windows版はMac版とほぼ同等の機能を持っています。加えて WSL2（Windowsの中でLinux環境を動かす仕組み）との連携が強いのが特徴です。

ただし、非エンジニアの方はWSL2を意識する必要はまったくありません。普通にWindowsのフォルダを選んで使えます。開発者が「Linux環境で動かしたい」ときの選択肢だと覚えておけば十分です。

深掘りデスクトップアプリ以外の入口（参考）

Codexには、同じ中身に対して複数の入口があります。このガイドは1つ目だけを扱いますが、名前だけ知っておくと会話についていけます。

  • デスクトップアプリ：このガイドの対象。いちばん親切な入口。
  • Web版：ブラウザから。GitHubと連携してクラウドで動かす使い方が中心。
  • IDE拡張：VS Code や Cursor などのコードエディタの中で使う。
  • CLI：黒い画面（ターミナル）から。上級者向け。npm install -g @openai/codex などで導入します。

【制約】

1. このフォルダの目的の要約（3行以内）
2. 主なファイル・フォルダの一覧と、それぞれの役割
3. 私が最初に知っておくべきことを3つ

これを送ると、Codexはフォルダの中を読み、調べ、まとめて返してきます。その「調べている過程」が画面に流れるのが、チャットとの決定的な違いです。ぜひ、その流れを眺めてみてください。

よい頼み方の型：4点セット

Codexへの依頼は、次の4つを書くと成功率が跳ね上がります。逆に、うまくいかない依頼はたいていこのどれかが抜けています。

要素意味書き方の例

制約やってほしくないこと「元のPDFは絶対に変更しないでください」
完了条件どうなったら終わりか「CSVが1つでき、行数が30になっていること」

← 表は横にスクロールできます

とくに効くのが完了条件です。これがないと、Codexは「たぶんこれで終わりかな」と自己判断します。「どうなったら成功か」を書くだけで、途中で勝手に終わることが激減します。

・議事録フォルダの中に「一覧.csv」ができている
・日付の新しい順に並んでいる
・各行に「日付・会議名・ファイル名」の3列がある

第4章へ：AIはどこで動いている？

Chapter 04

AIは、
どこで動いている？

Codexの作業場所には種類があります。ここを知らないと「なぜPCを閉じたら止まったのか」「なぜ結果が反映されないのか」が永遠に謎のままです。

3行でいうと

  • ローカル＝あなたのPCの中で動く。PCを閉じると止まる。
  • クラウド＝OpenAIのサーバーで動く。PCを閉じても進む。
  • まずはローカルで十分。この2つの違いだけ、押さえてください。

🏠 たとえるなら

ローカルは、自宅の作業机。目の前に材料があり、すぐ手に取れます。仕上がりもその場で確認できます。ただし——あなたが家を出れば（PCを閉じれば）、作業は止まります。

クラウドは、貸しオフィス。材料のコピーを預けて「やっておいて」と頼み、あなたは帰宅します。翌朝オフィスに行くと、仕事は終わっています。ただし預けられるのは、コピーを渡せる素材だけ。

ワークツリーは、隣の空き部屋をもう1つ借りること。同じ資料のコピーを持ち込んで、Aの作業とBの作業を別々の部屋で進めれば、書類が混ざりません。

3つの作業場所

※ このあと「Git（ギット）」「GitHub（ギットハブ）」という言葉が出ます。Gitは「ファイルの変更履歴を全部記録して、いつでも前に戻せるようにする仕組み」、GitHubは「その記録をインターネット上に置いて共有する場所」です。いまはこれだけで十分です。

ローカル

あなたのPC

  • PC上のファイルを直接読み書き
  • 結果がすぐ手元に反映される
  • アプリを閉じると止まる
  • Gitなどの準備が要らない

クラウド

OpenAIのサーバー

  • PCを閉じても作業が進む
  • GitHubとの接続が前提
  • 結果は後から取り込む
  • 長時間の仕事に向く

ワークツリー

作業用のコピー

  • 同じ素材から別の作業場を作る
  • 複数の作業を同時に進められる
  • 元のファイルを汚さない
  • Gitの仕組みを利用

どこで切り替えるのか

依頼を書く入力欄のすぐ上に、作業フォルダ名と並んで「ローカル」と表示されています。ここが切り替えの場所です。その横にあるのは、いま作業している枝分かれ（ブランチ）の名前です。

どっちを選べばいい？

迷ったら、この順で考えてください。

  1. 初めてなら、まずローカル

    準備が少なく、結果がその場で見えます。学習には圧倒的にこちらが向いています。

  2. 「終わるまで待てない長さ」ならクラウド

    数十分かかる作業を頼んで、PCを閉じて出かけたいとき。ただしGitHubとの接続が必要です。

  3. 複数の作業を同時に走らせたいならワークツリー

    AとBを並行させると、同じファイルを取り合って事故ります。ワークツリーはそれを防ぐための「部屋の増設」です。

!

クラウドに預けるということは、コピーを外に出すということです。社外秘のファイルや個人情報を含むフォルダを扱うときは、会社のルールを必ず確認してください。判断に迷ったら、ローカルにしておけば安全側に倒せます。

深掘りそもそもGit・GitHubって何？（1分で）

Gitは、ファイルの変更履歴を記録する仕組みです。「いつ・誰が・どこを・どう変えたか」を全部覚えていて、いつでも過去に戻せます。超高機能な「元に戻す」ボタンだと思ってください。

GitHubは、そのGitの記録をインターネット上に置いて共有できるサービスです。クラウド実行では、この置き場所を通じてファイルをやりとりします。

そしてワークツリーは、Gitの機能のひとつ。同じ記録から「もう1つの作業フォルダ」を作り出せる仕組みです。だからワークツリーはGitがある場所でしか使えません。

非エンジニアの方へ：Gitを覚える必要はいまはありません。ただ「元に戻せる仕組みがあると、AIに任せるのが一気に安全になる」ということだけ、頭の隅に置いてください。

深掘りデータはどこに保存されているのか

ローカルで使う場合、やりとりの履歴はあなたのPC内（多くは ~/.codex）に保存されます。スキル（第8章）は、個人用が ~/.agents/skills、チーム共有用がプロジェクト内の .agents/skills に置かれます。

~ は「あなたのユーザーフォルダ」を表す記号です。Macなら /Users/あなたの名前、Windowsなら C:\Users\あなたの名前 にあたります。

※ 保存先はバージョンによって変わることがあります。

ここだけ覚えて

  • ローカル＝自宅の机（閉じたら止まる）、クラウド＝貸しオフィス（閉じても進む）。
  • 最初はローカルで十分。クラウドは「待てない長さの仕事」用。
  • クラウドはファイルのコピーを外に出す。機密情報の扱いは事前に確認を。
  • 同じフォルダで2つの作業を同時に走らせたくなったら、作業用のコピー（ワークツリー）という手があると思い出す。いまは名前だけで十分です。
第5章へ：タスクとプロジェクト

Chapter 05

タスクと、
プロジェクト

Codexを使いこなす人と、そうでない人の差は、じつは「仕事の分け方」にあります。技術ではなく、整理整頓の話です。

3行でいうと

  • プロジェクト＝関連するものをまとめる箱。
  • タスク＝1つの仕事であり、1つの会話。サイドバーの「新しいチャット」から始めます。
  • 鉄則は「1タスク1用件」。これだけで結果が変わります。

🗂 たとえるなら

プロジェクトは、キャビネットの引き出し1段。「Aプロジェクト」の書類はここ、と決めておく場所です。関連する会話・ファイル・作業がここにまとまります。

タスクは、1回の打ち合わせ。1つのテーマについて話し、その場で仕事を片づけます。「議事録を作る」「請求書をまとめる」——1つの成果に対して、1つのタスクです。

打ち合わせに関係のない話題を持ち込むと、話がとっ散らかりますよね。Codexもまったく同じです。

プロジェクトの作り方

左のサイドバーの「プロジェクト」を開くと、一覧が「名前」と「更新日」で並びます。新しく作るときは右上の「作成」から。作業フォルダごとに1つ作っておくと、あとから探しやすくなります。

※ 使わなくても Codex は動きます。最初は作らなくて構いません。「関連する作業が増えてきたな」と感じたら作る、くらいで十分です。

なぜ「1タスク1用件」なのか

これは、このガイドで2番目に大事なルールです（1番目は第1章の「聞くのではなく頼む」）。

1つのタスクに複数の用件を混ぜると、Codexの頭の中がごちゃごちゃになります。理由は次章の「コンテキスト」で詳しく説明しますが、結果だけ先に言うと——混ぜるほど、精度が落ちます。

✕ よくない

全部ひとつの会話で

「議事録を索引化して。あ、ついでにこのバグも直して。そういえば READMEも書き換えてくれる？」

→ どれも中途半端になり、前の話を忘れ、途中で矛盾しはじめます。

◎ よい

用件ごとに新しい会話

議事録の索引 → タスクA
バグ修正 → タスクB
README → タスクC

→ それぞれが集中して仕上がり、あとから見返すのもラクです。

新しい用件を思いついたら、その場で頼まず、新しいタスクを立てる。慣れるまでは意識的にやってみてください。効果はすぐ実感できます。

仕事の流れ：依頼 → 作業 → レビュー

  1. 依頼する

    第3章の4点セットで頼みます。可能なら「まず計画だけ」を添えて。

  2. Codexが作業する

    ファイルを読み、書き、必要なら実行して試します。要所であなたに承認を求めます。

  3. レビュー（確認）する

    何がどう変わったかの一覧（差分／diff）が出ます。ここを見るのが、あなたの一番大事な仕事です。

  4. 採用するか、直させるか決める

    よければ確定。違えば「ここをこう直して」と具体的に伝えます。

i

レビューキューという考え方。自動化（第10章）などで複数の作業が同時に終わると、結果は「確認待ちの列」に溜まります。これをレビューキューと呼びます。Codexは「勝手に完了させる」のではなく「確認してもらう列に並べる」——この設計思想を知っておくと安心できます。

差分（diff）の読み方

差分は、「変更前」と「変更後」を並べた表示です。読むときのポイントは3つだけです。

  • 緑（＋）は追加された行、赤（−）は削除された行。色の意味さえ分かれば、あとは日本語を読むのと同じです。
  • ファイルの数を先に見る。「3ファイルだけ直すはずが20ファイル変わっている」なら、そこで止めます。
  • 意図しないファイルが混ざっていないか。これがいちばん重要なチェックです。

内容が理解できなくても構いません。「頼んでいない範囲に手が入っていないか」だけ見る——これで事故の大半は防げます。

深掘り過去の作業を探して、再開する

過去のタスクは履歴から検索でき、途中から再開できます。「先週やったあの作業、どうやったんだっけ」を掘り返せるので、タスクに分かりやすい名前をつけておくと後で効きます。

「1タスク1用件」を守っていると、この検索が驚くほど効率的になります。逆に全部混ぜていると、目的の情報が長い会話に埋もれます。整理は、未来の自分への投資です。

深掘りブランチという言葉が出てきたら

ブランチは Git の用語で、「本線から枝分かれした作業ライン」のことです。

本の原稿でたとえると、本線が「入稿する原稿」。ブランチは「別ファイルに保存した改訂案」です。気に入ったら本線に取り込み、ダメなら捨てればいい。本線を汚さずに試せる仕組みだと思ってください。

Codexは、変更を専用のブランチで行うことがあります。これはあなたの元のファイルを守るための配慮です。怖がる必要はありません。

ここだけ覚えて

  • 1タスク1用件。用件を思いついたら、混ぜずに新しいタスクへ。
  • あなたの一番の仕事は依頼することではなく、差分を確認すること。
  • 差分では「頼んでいない範囲が変わっていないか」だけ見ればOK。

モデル
― AIの「頭脳」を選ぶ

この章は応用編です。読まなくても第7章から問題なく続きます。まず使ってみたい方は、飛ばして構いません——「結果は悪くないけど、なんだか遅い／もったいない気がする」と感じたときに戻ってきてください。

Codexの中で動く「頭脳」は、じつは差し替えられます。ここを知らないと、簡単な用事に高級な頭脳を使って無駄に消費したり、難しい仕事に軽い頭脳を当てて失敗したりします。

3行でいうと

  • モデル＝AIの頭脳。種類によって賢さ・速さ・コストが違います。
  • Codexには Sol / Terra / Luna の3つ。迷ったら真ん中の Terra。
  • それとは別に、「推論レベル」（どれだけ考えるか）も選べます。つまみは2つ。

🚗 たとえるなら

車を選ぶのと同じです。Sol は大型SUV——悪路でも走破しますが、燃費は悪い。Terra はセダン——毎日の足として過不足がない。Luna は原付——近所の用事なら、いちばん速くて安い。

コンビニに大型SUVで行く必要はないし、山道に原付で行ってはいけない。それだけの話です。

そもそも「モデル」とは何か

モデルとは、AIの本体そのものです。大量の学習の結果できあがった「頭脳」で、ChatGPTの画面に「GPT-5.6」などと表示されているのが、これにあたります。

ここが大事なところです。Codexというアプリと、その中で動くモデルは、別のものです。

Codex

車体

ファイルを読む、コマンドを動かす、承認を求める——といった「体」の部分。これは変わりません。

モデル

エンジン

実際に考える部分。ここを積み替えると、賢さ・速さ・コストが変わります。

3つのモデル

モデルひとことで向いている仕事使える回数の目安
Luna速くて安い手順がはっきりした繰り返し。抽出・分類・変換・決まった形の要約多い
Terraバランス型・ふだん使いふつうの作業、調査、修正、確認。日々の仕事の大半中くらい
Solいちばん賢い・切り札あいまいで難しい仕事、原因不明の調査、失敗が高くつく判断少ない

← 表は横にスクロールできます

※ 使える回数はプランと時期で変わります。2026年8月時点の Plus では、5時間あたり Sol が 10〜100回、Terra が 25〜200回、Luna が 250〜2,000回が目安とされています（幅があるのは、1回の仕事の重さで変わるためです）。賢いモデルほど、同じプランで使える回数は減ります。

!

選べるモデルは、プランによって違います。いちばん賢い Sol は上位プラン向けで、無料プランの一覧には出てきません。また一覧には、旧世代のモデル（5.5、5.4 Mini など）が並んでいることもあります。自分の一覧に何が出ているかを、まず見てみてください。無ければ、その環境では使えないということです。

つまみは2つある ── モデルと「推論レベル」

ここが多くの人が混同するところです。「どのモデルを使うか」と「どれだけじっくり考えさせるか」は、別々のつまみです。後者はアプリの画面で「推論レベル」と表示されています。

推論レベルは、答える前にどれだけ考え込むかの設定です。日本語表示では「低／中／高」のように出ます（英語では Light（CLIでは Low）／Medium／High／Extra High／Max／Ultra）。既定は「中」（Medium）。呼び名や段階の数は版によって変わります。

※ 上の図は「低／中／高」の3段階で描いていますが、その上に Extra High・Max・Ultra があります。この3つは、当面は使わなくて構いません——非常に難しい仕事のための特別枠です。

深く考えるほど結果は良くなりやすいのですが、時間もトークンも増えます。公式の考え方はシンプルで、「必要な品質が出るいちばん低い設定から始めて、足りなければ上げる」です。

仕事別・こう選ぶ

Luna が向く

  • ファイル名を一覧にする
  • 議事録から決定事項だけ抜き出す
  • 表の形式を変換する
  • 決まったフォーマットに整える

Terra が向く（大半）

  • 資料を読んで要約と改善案を出す
  • ふつうの修正・調整
  • 「これどうなってる？」の調査
  • 作ったものの確認

Sol が向く

  • 原因がまったく分からない不具合
  • 「どう作るべきか」から相談する
  • 間違えると影響が大きい変更
  • 他のモデルで2回失敗したとき

切り替え方と、迷ったときの手順

モデルと推論レベルは、依頼を書く入力欄のすぐ下・右寄りにまとまっています。「5.6 Terra 中」のように、モデル名と推論レベルが並んで表示されているので、そこをクリックします。

開くと 「モデル」「推論レベル」「詳細設定」 の3つが並びます。「モデル」を選ぶと使えるモデルの一覧が、「推論レベル」を選ぶと深さの一覧が出ます。この2つが別々の項目として並んでいるのを見れば、「つまみが2つある」という話がそのまま画面に現れているのが分かります。

※ CLIでは /model と打ちますが、アプリにこのコマンドはありません。

  1. まず Terra ＋ 推論レベル「中」（既定）で試す

    これが基準点です。何も考えずここから始めて構いません。

  2. うまくいったら、次は Luna に下げてみる

    同じ品質が出るなら、そのまま Luna で回せば安く速くなります。上げるより先に、下げてみる。

  3. 2回試してダメなら、推論レベルを上げる

    モデルより先に、こちらを上げるほうが費用対効果が高いことがよくあります。

  4. それでもダメなら Sol

    切り札は、切り札として取っておく。ここまで来たら遠慮なく使ってください。

!

クラウド側ではモデルを選べません。第4章で説明した「クラウド実行」のチャットでは、既定のモデルを変更できないと公式に明記されています。モデル選びが効くのは、手元（デスクトップアプリ・IDE・CLI）での作業だけだと考えてください。

深掘りなぜ賢いモデルほど高いのか

賢いモデルは、答える前に頭の中でたくさん考えます。そしてこの「考えている内容」も、じつはトークンとして消費されます（第7章）。

つまり「賢い」＝「たくさん考える」＝「たくさんトークンを使う」という、素直な関係になっています。推論レベルを上げると高くなるのも、まったく同じ理由です。

もうひとつ、モデルごとの単価そのものも違います。同じ1トークンでも、賢いモデルほど高く設定されています（Sol と Luna では入力の単価に20倍以上の開きがあります）。「たくさん考える」×「1回あたりが高い」の掛け算だと思ってください。

逆に言えば、答えが一本道の作業では、たくさん考えても意味がありません。だから軽いモデルで十分なのです。

深掘りモデルの名前は、これからも変わります

モデルには世代交代があります。古いものは順次引退し、新しいものが入ります。たとえば GPT-5.4 系は 2026年8月末で Codex 向けの提供を終える予定とされています。

ですから「Sol」「Terra」「Luna」という名前は、いずれ変わります。覚えるべきは名前ではなく、「賢い／ふだん使い／軽い」の3レーンに分かれている、という構造のほうです。この構造は当分変わりません。

新しい名前が出てきたら、「これはどのレーンだろう？」と考えれば、それだけで使い分けられます。

ここだけ覚えて

  • モデル＝AIの頭脳。Sol＝切り札／Terra＝ふだん使い／Luna＝軽作業。
  • つまみは2つ。画面では「モデル」と「推論レベル」として並んでいます。
  • 迷ったら Terra ＋ 推論レベル「中」。うまくいったら下げてみる。上げるのは詰まったときだけ。
  • 選べるモデルはプランによって違います。クラウド実行では選べません。
  • 覚えるのは名前ではなく「賢い／ふだん／軽い」の3レーンという構造。名前は変わります。
第7章へ：コンテキストとトークン

Chapter 07

コンテキストと
トークン

ここは少しだけ理屈っぽい章です。でも、「なぜAIは途中からバカになるのか」の答えがここにあります。知っている人と知らない人で、成果がいちばん変わる場所です。

3行でいうと

  • トークン＝AIが文章を数える単位。「机にどれだけ載るか」と「今月あとどれだけ使えるか」の両方を、この単位で数えます。
  • コンテキスト＝AIが一度に覚えていられる範囲。机の広さです。
  • 机が散らかると仕事が雑になる。だからこまめに片づける。

🪑 たとえるなら

AIの頭の中を、一枚の作業机だと思ってください。

あなたが渡した指示、読み込んだファイル、これまでの会話——全部がこの机の上に広げられます。これがコンテキストです。

机の広さには限りがあります。書類を置きすぎると、古いものが端に押しやられ、AIは「さっき決めたこと」を見失います。人間と同じで、散らかった机では、いい仕事はできません。

そしてトークンは、机に載っている書類の「枚数」の数え方です。同じ単位で「今月あと何枚ぶん頼めるか」も数えますが、そちらは別の話。のちほど分けて説明します。

トークンとは、要するに何か

AIは文章を「文字」ではなく、トークンという細かいかたまりに分けて処理します。おおまかな目安はこうです。

内容おおよそのトークン数
日本語の文章1文字あたり おおよそ 1トークン前後
英語の文章1単語あたり おおよそ 1〜1.5トークン
この章くらいの長さ数千トークン
そこそこの長さのファイル1本数千〜数万トークン

← 表は横にスクロールできます

※ 正確な数え方は言語や内容で変わります。厳密な数字を覚える必要はまったくありません。「長い文章＝たくさん消費する」という感覚だけで十分です。

なぜAIは、長く話すと調子が悪くなるのか

長時間ひとつのタスクで作業していると、こんなことが起きます。

  • さっき直したはずの問題を、もう一度作ってしまう
  • 序盤に決めたルールを、途中から守らなくなる
  • それでいて、自信満々に間違える

これはコンテキストが埋まってきたときに起きる、よく知られた現象です（英語圏では context rot＝文脈の腐敗、と呼ばれます）。厄介なのは、エラーが出ないこと。止まらないので、気づきにくいのです。

対策は、たった3つ

対策 1

用件が変わったら、新しいタスク

第5章の「1タスク1用件」は、じつはこの対策そのものです。いちばん効きます。アプリでは、サイドバーの「新しいチャット」から始められます。

対策 2

長くなったら圧縮する

これまでの会話を要約して、机の上を整理する機能があります。いつも依頼を書いている入力欄に /compact とだけ打って送ると実行できます（先頭のスラッシュが目印です）。作業を中断せずに片づけられます。

対策 3

必要なものだけ渡す

「フォルダ全部見て」ではなく「このファイルとこのファイルを見て」。渡す量が減れば、それだけ長持ちします。

なお、机が埋まりきる前に自動で要約が走る仕組みもあります（自動コンパクション＝自動での机の片づけ、という意味です）。ただし要約は完璧ではなく、細部は落ちます。自動任せにせず、区切りのいいところで自分から新しいタスクに移るほうが、結果は確実に良くなります。

i

ここから、トークンの話が2つに分かれます。ここまで話してきたのは「一度に机に載せられる量」——1回の会話でAIが覚えていられる範囲の話でした。ここから話すのは「今月あと何回頼めるか」——プランごとの使用量の話です。同じトークンという単位で数えますが、別のものです。机がいっぱいになってもプランの上限とは関係ありませんし、その逆もあります。

コスト：使える量には上限があります

Codexは、ChatGPTのプランに含まれています（Free / Go / Plus / Pro / Business / Enterprise）。ただし使える量はプランによって大きく違います。

Plus週に数回、集中して作業できる程度
Pro（$100）Plus のおよそ5倍
Pro（$200）Plus のおよそ20倍
Business公表されている範囲は Plus と同等（ただし下の注意書きを必ず確認）
Enterprise / Edu固定の上限はなく、追加分の利用枠（クレジット）に応じて拡張

!

会社で Business プランを使っている方へ。Business は、契約した時期によって Codex が使えたり使えなかったりします。目安は2026年6月24日。それ以前から Codex を追加していた会社は、いまも使えます。それ以降に新しく契約した会社では、Codex は含まれていません。「Business なら入っているはず」で話を進めると行き違いが起きるので、まず社内のIT担当か管理者に「うちは Codex を使えますか」と一言確認してください。

i

節約と精度は、同じ方向を向いています。「余計なものを渡さない」「用件ごとに分ける」——これはコスト削減の話であると同時に、結果の質を上げる話でもあります。ケチるほど賢くなる、という珍しい構造です。

トークンを節約する7つの技

ここはこの章でいちばん実用的な部分です。上から順に、効果の大きい順に並べました。1と2だけでも、体感がはっきり変わります。

  1. 用件ごとにタスクを分ける

    効果は断トツです。会話が長いほど、これまでの全部を毎回読み直しています。用件が変われば新しいタスク——それだけで消費が大きく変わります。

  2. 渡す範囲を絞る

    「このフォルダ全部を見て」ではなく「この3つのファイルを見て」。読ませた量が、そのまま消費量です。探させるより、教えたほうが安い。

  3. モデルと推論レベルを下げる

    第6章の話です。決まりきった作業に賢いモデルを使うのは、コンビニに大型SUVで行くのと同じ。まず下げてみて、足りなければ上げる。

  4. 使わないスキル・外部接続をオフにする

    スキル（第8章）も外部接続（第9章）も、「一覧」が毎回コンテキストに載ります。使っていないものは、黙って机を狭くし続けています。定期的に見直しを。

  5. AGENTS.md に決まりごとを書いておく

    毎回同じ前提を説明していませんか。それを1枚のファイルにまとめておけば、説明の手間ごと消えます（第8章）。

  6. 長くなったら /compact、区切りで新しいタスク

    要約して圧縮する。ただし要約でも細部は落ちるので、区切りのいいところで新しくするほうが、確実で安上がりです。

  7. 完了条件を書く

    意外に思われますが、これが効きます。やり直しは、まるごと二重に消費します。一発で通す依頼文が、結局いちばん安い（第3章）。

!

いま何を消費しているか、確認できます。入力欄に /status と打つと、コンテキストの使用量や利用上限が見られます。節約の第一歩は、測ること。「なんとなく重い」で悩む前に、一度見てみてください。

やりがちな、もったいない使い方

✕ もったいない

  • ひとつのタスクで1日じゅう作業する
  • 毎回「このプロジェクトは〜」から説明し直す
  • とりあえずフォルダ全体を読ませる
  • 簡単な整形にいちばん賢いモデルを使う
  • 試したいプラグインを入れっぱなしにする

◎ かしこい

  • 用件が変わったら新しいタスク
  • 共通の前提は AGENTS.md に一度だけ書く
  • 対象のファイルを名指しする
  • 軽い作業は軽いモデルに任せる
  • 使わない接続とスキルは定期的にオフ
深掘りコンテキストの具体的な大きさ（数字が気になる人へ）

Codexで扱えるコンテキストの上限は、モデルとバージョンによって変わります。2026年時点では、上限として40万トークン規模が設定されています。この枠は年々調整されていて、2026年7月にも入力側の上限が引き下げられました。

これは制限というより設計判断です。枠を広げすぎると、AIは「広い机の端にある書類」を見落としやすくなり、かえって精度が落ちます。適度な広さに保ち、埋まる前に要約する——そのほうが安定するのです。

※ こうした数値は頻繁に変わります。覚える必要はありません。「上限があり、埋まる前に片づけるのが良い」という原則だけが本質です。

深掘り覚えておくと便利なコマンド

依頼を書く入力欄に、先頭がスラッシュの言葉を打つと使えます。アプリで使えるものと、CLI（黒い画面から文字で操作する上級者向けの入口）専用のものがあるので、そこだけ注意してください。

アプリでは、新しいタスクはサイドバーの「新しいチャット」から始めます。困ったら新しい机、が基本戦略です。

ここだけ覚えて

  • コンテキスト＝AIの机の広さ。散らかると、静かに精度が落ちます。
  • AIが急におかしくなったら、まず新しいタスク。これで大半が直ります。
  • トークンは2つの意味で使われます。「机にどれだけ載っているか」と「プランを今月どれだけ使ったか」。渡す量を絞れば、どちらにも効きます。
  • プランごとに上限があります。公式の料金ページで最新を確認する癖を。
第8章へ：スキル

Chapter 08

スキル

ここからは「使える」から「使いこなす」への段階です。スキルを理解すると、Codexはあなた専用の助手に変わります。

3行でいうと

  • スキル＝Codexに渡しておく「業務マニュアル」。
  • 一度書けば、毎回同じ品質で同じ手順を再現してくれます。
  • 自分で書けます。しかも作るのもCodexに手伝ってもらえます。

📘 たとえるなら

新しく入った助手に、毎回ゼロから「うちのやり方」を説明するのは大変です。「これがうちのマニュアルです。この通りにやってください」と一冊渡せたら、ずっと早い。

スキルは、まさにそのマニュアルです。手順・お手本・注意点をまとめておくと、Codexは毎回それを読んでから仕事を始めます。あなたの「暗黙のルール」を、形にして預けられるということです。

スキルの正体は、ただのフォルダとファイル

構えなくて大丈夫です。スキルの実体は、フォルダの中に置かれた1枚の説明書です。

スキルの中身（例）
議事録まとめ/
├── SKILL.md      ← 手順を書いた説明書（これが本体）
├── サンプル.md    ← お手本（あると精度が上がる）
└── scripts/      ← 必要なら補助プログラム（なくてもいい）

※ .md は「マークダウン」という、メモ帳でも開ける軽い文書ファイルの形式です。中身はただの文字なので、身構える必要はありません。

中心にあるのが SKILL.md。ここに「何のためのスキルか」「どういう手順でやるか」を、ふつうの日本語で書きます。プログラムを書く必要はありません。

ただし、最初の5行だけ決まった書き方があります。いちばん上と、その4行下にある --- で挟んだ部分は、このスキルの「名札」です。name（スキルの名前）と description（どんなときに使うものか）の2つだけ、この形で書いてください。ここから下は、全部ふつうの日本語で構いません。--- も含めて下の例をそのままコピーし、名前と説明だけ書き換えるのがいちばん簡単です。

---
name: 議事録まとめ
description: 会議のメモから、決定事項とToDoを抽出して整形する
---

# 議事録まとめ

## いつ使うか
会議の生メモを渡されたとき。

## 手順
1. メモ全体を読み、話題ごとに区切る
2. 「決定したこと」と「まだ決まっていないこと」を分ける
3. ToDo は「誰が・何を・いつまでに」の形にそろえる
4. 発言者の個人名は、社外共有用では役職に置き換える

## 出力の形
- 冒頭に3行の要約
- 決定事項（箇条書き）
- ToDo（表形式：担当 / 内容 / 期限）
- 保留事項

## 注意
- メモに書かれていないことを推測で補わない
- 不明点は「要確認」と明記する

見てのとおり、後輩に渡す引き継ぎメモとほとんど同じです。これがスキルです。

いま入っているスキルを見る

左のサイドバーの「プラグイン」を開くと、画面の上部に 「プラグイン」「スキル」 という2つのタブがあります。スキルの一覧は、この「スキル」タブです。ここで有効・無効を切り替えられます。

置き場所は2種類

個人用

~/.agents/skills

自分だけが使うスキル。どのプロジェクトからでも呼び出せます。

チーム共有

<プロジェクト>/.agents/skills

プロジェクトの中に置くと、そのプロジェクトを共有している人みんなが使えます。チームのやり方を統一できます。

※ ~ は「あなたのユーザーフォルダ」を表す記号です（Macなら /Users/自分の名前、Windowsなら C:\Users\自分の名前）。
※ 先頭が「.」で始まるフォルダは、通常は非表示です。Macは Finder で Command + Shift + .、Windowsはエクスプローラーの「表示」→「隠しファイル」で表示できます。
※ 保存先はバージョンによって変わることがあります。アプリの設定画面から確認するのが確実です。

呼び出し方

  • 名前で指定する。依頼文の中で $議事録まとめ のように、スキル名の前に半角の $ を付けて呼ぶと、そのスキルを使ってくれます。
  • 自動で使ってくれる。状況に合っていれば、Codexが自分で判断して使うこともあります。

確実にやってほしいときは名前で明示的に呼ぶのが安全です。

※ この $ はCodexでの書き方です。同じアプリでも Chat／Work モードでは @ を使いますが、いまは覚えなくて構いません。

スキルを作るタイミング

同じことを2回頼んだときは、まだ指摘で足ります。3回目が来たら、それはスキルにするサインです。「毎回これを注意している」ということは、それがあなたの暗黙のルールだということ。一度マニュアルに書けば、二度と言わずに済みます。

書き方が分からなければ、Codexに作らせることもできます（下の「深掘り」を参照）。

最初から用意されているスキルもあります

ゼロから作らなくても、公式が提供しているスキルがあります。たとえば——

  • デザインデータ（Figma）から、実際に動くコードを起こす
  • プロジェクト管理ツール（Linear など）と連携する
  • 作ったものを公開する（Vercel / Netlify / Cloudflare など）
  • PDF・表計算・文書ファイルを扱う（非エンジニアにはこれが効きます）
!

増やしすぎ注意。スキルは便利なので、つい溜まります。使わないスキルが増えると、Codexが毎回その一覧を読み込むぶん、机（コンテキスト）を圧迫します。使わないスキルは、消さなくても設定画面から「無効化」できます。オフにしておけば、必要になったときに戻せます。スキルが多すぎると、Codexが一覧を読みきれず「一部を省きました」という警告が出ることがあります。その警告を見たら、使っていないものを無効化するサインだと思ってください。

もうひとつの置き手紙：AGENTS.md

スキルと並んで、ぜひ知っておいてほしいファイルがあります。AGENTS.md（エージェンツ・ドット・エムディー）です。

📋 スキルとの違い

スキルが「業務マニュアル」なら、AGENTS.md は「就業規則」です。

マニュアルは特定の作業のときだけ開きます。就業規則はこの職場にいるあいだ、ずっと効いている。AGENTS.md はそういうファイルです。プロジェクトの入口に1枚置いておくと、Codexは作業を始める前にこれを読みます（ただし長すぎると途中までしか読まれないことがあるので、簡潔に書くのがコツです）。

書くのは、毎回言っている決まりごとです。

AGENTS.md の例
# このプロジェクトについて

社内向けの業務マニュアルを管理しているフォルダです。

## 守ってほしいこと
- 文体は「です・ます」で統一する
- 専門用語を使うときは、初出でカッコ書きの説明を添える
- 数字を書くときは、必ず出典のファイル名を併記する

## 触らないでほしい場所
- archive/ フォルダ（過去版の保管庫。読むのはOK、変更は禁止）
- 承認済み/ フォルダ（法務確認済みのため変更禁止）

## 作業の進め方
- 変更したら、必ず変更点の一覧を最後に示すこと
- 判断に迷ったら、勝手に決めずに質問すること

効果は2つあります。ひとつは結果が安定すること。もうひとつが見逃されがちですが、毎回同じ説明を書かなくて済むぶん、トークンが減ることです。AGENTS.md を整えるだけで出力トークンの中央値が約17%、作業時間の中央値が約29%減ったという検証結果もあります（10のプロジェクト・124件の変更を、AGENTS.md のあり／なしで比較した2026年の研究）。

置き場所は、まずプロジェクトのいちばん上の階層。ファイル名は AGENTS.md です。フォルダごとに追加で置くこともでき、その場合は上の階層から順に読まれて、下のものが優先されます。中身はただの文章なので、メモ帳で書けます。

i

使い分けの目安。「この作業のときだけ守ってほしいこと」→ スキル。「この場所で作業するなら、いつでも守ってほしいこと」→ AGENTS.md。迷ったら AGENTS.md に書いて、あとで分けても構いません。

深掘りスキルをCodexに作ってもらう

「書き方が分からない」なら、Codexに書かせればいいのです。スキルを作るためのスキルが用意されています。

依頼例
$skill-creator

「会議メモから議事録を作る」スキルを作りたいです。
私のこだわりは次のとおりです。

・決定事項と保留事項を必ず分ける
・ToDoは「誰が・何を・いつまでに」の形式にする
・社外共有版では個人名を役職に置き換える
・メモにないことは推測で補わず「要確認」と書く

これを SKILL.md の形にまとめてください。

できあがったものを読んで、違うところを直す。この進め方がいちばん早いです。

深掘りよいスキルを書くコツ
  • 「いつ使うか」を最初に書く。これがないと、Codexが自動で使う判断をできません。
  • お手本を1つ入れる。言葉で10行説明するより、完成例を1つ見せるほうが正確に伝わります。
  • やってほしくないことを書く。「推測で補わない」のような禁止事項は、非常によく効きます。
  • 長くしすぎない。スキルもコンテキストを消費します。1スキル1目的で、短く。
  • 実際に使いながら育てる。失敗したら、その原因をスキルに1行足す。これを繰り返すと、驚くほど賢くなります。
深掘り「プラグイン」「MCP」という言葉について

スキルの近くで、プラグインや MCP という言葉を見かけることがあります。ざっくりした違いはこうです。

  • スキル＝やり方を教えるマニュアル（知識・手順）
  • MCP / プラグイン＝外部サービスとつなぐ配線（道具・接続）

MCP は Model Context Protocol の略で、AIと外部ツールをつなぐための共通規格です。「うちの社内システムのデータも見られるようにする」といった拡張に使われます。

非エンジニアの方は、いまはスキルだけ理解していれば十分です。MCPは必要になったときで間に合います。

ここだけ覚えて

  • スキル＝Codexに渡す業務マニュアル。中身はただの説明文（SKILL.md）。
  • 同じ依頼を3回以上したら、それはスキルにするサイン。
  • 書き方が分からなければ、Codexに作らせる（$skill-creator）。
  • 使わないスキルは消さずに無効化。机を広く保つためです。
  • 現場ぜんぶの決まりごとは AGENTS.md に。結果も安定し、トークンも減ります。
第9章へ：外部接続 ― MCPとプラグイン

Chapter 09応用編

外部接続
― MCPとプラグイン

この章は応用編です。読まなくても第10章から問題なく続きます。Codexを自分のパソコンの中だけで使うなら、不要です——「Slackや Drive とつなげたら便利なのに」と思ったときに戻ってきてください。

ここまでのCodexは、あなたのパソコンの中だけで完結していました。外のサービスとつなぐと、できることが一気に広がります。

3行でいうと

  • コネクタ・MCP・プラグイン＝Codexを外部サービスにつなぐ仕組み。
  • つなぐと「Slackに投稿」「Notionの資料を読む」「デザインを見て作る」ができます。
  • 非エンジニアはプラグインだけ覚えれば十分。1回で全部やってくれます。

🔌 たとえるなら

第8章のスキルが「やり方を書いたマニュアル」だったのに対して、こちらは「道具そのもの」です。

どんなに立派なマニュアルがあっても、工具箱に工具が入っていなければ作業はできません。外部接続は、その工具を増やす話です。

そしてプラグインは、工具・配線・説明書がセットになった「取り付けキット」。1箱買えば、必要なものが全部そろいます。

3つの言葉の関係

似た言葉が並びますが、関係はとても単純です。

つなぎ先

コネクタ（アプリ連携）

Slack、Gmail、Google Drive、GitHub など、既存のサービスへの接続。そのサービスにログインして許可すると使えます。

つなぎ方の規格

MCP

AIと外部ツールをつなぐための共通の決まりごと。いわば「AI界のUSB規格」。これに対応していれば、どんな道具でもつなげます。

まとめて入れる箱

プラグイン

スキル・コネクタ・MCP を1つにまとめたパッケージ。入れるだけで設定と認証まで済みます。ここだけ覚えればOK。

つまり、MCPは「規格」、コネクタは「接続先」、プラグインは「セット商品」。買い物にたとえるなら、規格を調べて部品を個別に買うこともできるけれど、たいていの人はセット商品を買えば済む、ということです。

    プラグインを入れたあとは、新しいタスクを開いてから依頼してください（入れる前に開いていたタスクでは有効になりません。「入れたのに使えない」の大半がこれです）。「Driveの〇〇という資料を読んで、要点をまとめて」のように書けば、Codexが自分で取りに行きます。

!

つなぐということは、鍵を渡すということです。ここは第11章の考え方がそのまま当てはまります。

  • 必要なサービスだけつなぐ。「とりあえず全部」は絶対にやらない。
  • 読み取りだけで足りることが多い。投稿・書き込みの許可は、本当に要るときだけ。
  • 会社のアカウントをつなぐ前に、社内ルールを確認する。個人アカウントとは話が違います。
  • 使わなくなった接続はオフにする。「プラグイン」画面の「インストール済み」から外せます。安全面だけでなく、次の理由からも重要です。

接続を増やすと、「この道具はこう使う」という説明書きが毎回コンテキストに載ります（第7章）。つまり使わない接続は、机を狭くし、精度を下げ、コストを上げます。スキルと同じで、増やしすぎ注意です。

深掘りMCPをもう少しだけ詳しく

MCP は Model Context Protocol の略です。仕組みはこうなっています。

  • 外部のツール側が「うちで使える道具の一覧」を、決まった形式で公開する
  • Codexがその一覧を読み込む
  • 必要になったら、Codexがその道具を呼び出す

ポイントは、この規格に対応してさえいれば、OpenAIが個別に対応しなくてもつながるところです。社内システムを自社でMCP対応にすれば、Codexから使えるようになります。

設定は config.toml というファイルに書きますが、非エンジニアの方が触る必要はありません。プラグインを使えば、この部分は自動でやってくれます。

深掘りスキル・プラグイン・AGENTS.md の使い分け

似たものが3つ出てきたので、整理しておきます。

　正体役割
スキル手順書特定の作業の「やり方」を教える
AGENTS.md就業規則この現場ぜんぶに共通する「決まりごと」
プラグイン取り付けキット外部サービスを使う「道具」を増やす

スキルと AGENTS.md は第8章で扱いました。知識を足すのが前2つ、能力を足すのがプラグインと覚えてください。

  • スキル＝やり方（知識）、外部接続＝道具そのもの（能力）。
  • 用語は3つあるが、プラグインだけ覚えればOK。設定も認証もまとめてやってくれます。
  • つなぐ＝鍵を渡すこと。必要なものだけ、できれば読み取りだけ。
  • 使わない接続はオフに。安全にも、コストにも、精度にも効きます。
第10章へ：スケジュール化（自動化）

Chapter 10

スケジュール化
（自動化）

ここまでは「頼んだら、やってくれる」でした。この章は「頼まなくても、やってくれる」。AIエージェントの本領はここから始まります。

3行でいうと

  • 自動化＝「指示＋スキル＋時刻」を登録すると、決めた時間に勝手に動く仕組み。
  • 結果は確認待ちの列（レビューキュー）に溜まります。勝手に確定はしません。
  • あなたのPCのフォルダを使う場合だけ、アプリの起動が必要です。ここが最重要の注意点。

🤖 たとえるなら

ロボット掃除機を思い浮かべてください。「毎朝8時に掃除」と設定すれば、あなたが何もしなくても動きます。

Codexの自動化も同じです。「毎朝9時に、昨日の変更点をまとめて」と登録すれば、朝には結果が用意されています。ただしCodexの自動化には、たとえが2つ要ります。

1つめは、いまのロボット掃除機。掃除する対象があなたの家（＝あなたのPCの中のフォルダ）なので、家の電気が通っていて、玄関が開いている——つまりPCが起きていて、アプリが立ち上がっている必要があります。

2つめは、留守番電話や自動転送。あなたの家とは関係なく、外の設備が勝手に動くタイプです。こちらはあなたが留守でも進みます。ただし、あなたの家の中にある書類は使えません。

自動化の3つの部品

部品 1

指示

何をしてほしいか。第3章の4点セットで書きます。ここは手抜きしない。

部品 2

スキル（任意）

第8章のマニュアル。付けると、毎回同じ品質で仕上がります。

部品 3

スケジュール

いつ動かすか。毎朝・毎週月曜・毎月1日など。

2種類の自動化（ここが一番大事）

自動化には、デスクトップアプリで動くものとWeb側（OpenAIのサーバー）で動くものの2種類があります。第4章の「ローカルとクラウド」が、そのまま自動化にも当てはまります。

※ ここでいう「Web側」とは、ブラウザで開くCodexの画面のことです（第2章の深掘りで触れた「Web版」）。デスクトップアプリとは別の画面で、あなたのPCのフォルダは見えません。そのかわり、その画面に事前にアップロードしておいた資料や、つないでおいたサービスを使って作業します。

結果どちらもレビューキューに入り、あなたの確認を待ちます

← 表は横にスクロールできます

つまり、「PCを閉じて寝ている間に、自分のPCのフォルダを触ってもらう」はできません。PCのファイルを使わない仕事なら、Web側のスケジュールに登録すればPCを閉じていても動きます。「自分のPCのファイルが必要かどうか」が分かれ目だと覚えてください。ここを勘違いすると「設定したのに動かない」と悩むことになります。

!

自動化は「無人」で走ります。スケジュール実行では、あなたが横で見ていません。つまりその場で承認を求めることができず、あらかじめ決めておいた権限の設定のまま動きます。だからこそ、自動化を登録する前に承認の設定を確認してください（次章）。

自動化するまえの、絶対のルール

  1. まず手動で1回、実行してみる

    まず手で試すのが確実です。期待どおりに動いたものだけを、スケジュールに登録します。

  2. 読み取り中心の内容から始める

    「まとめる」「一覧にする」「報告する」など。最初から「削除する」「送信する」を自動化しないでください。

  3. 権限は最小限にしておく

    ファイルの変更やネットワークへの接続を、必要な範囲だけに絞ります（第11章）。とはいえ「一覧表を作る」「下書きを作る」といった自動化は、新しいファイルを作る権限が要ります。コツは、書き込みを許すのは「新しく作る専用のフォルダ1つ」だけにしておくこと。既存の資料は読むだけ、出力は決めた1か所だけ——これなら無人でも安心です。

  4. しばらくは、結果を毎回見る

    自動化は「見なくていい」ではなく「見る量を減らす」仕組みです。安定するまでは必ず確認を。

実際に使える自動化の例

開発者向け

  • 毎朝、昨日の変更点をまとめて朝会用のメモにする
  • 新しく届いた課題を分類して優先度をつける
  • 自動テストが失敗した原因を要約する
  • リリース時の変更履歴の下書きを作る

非エンジニアでも

  • 指定フォルダに増えた資料を、週次で一覧表に追記する
  • 複数の文書を読んで、週報の下書きを作る
  • フォルダ内の書類の抜け漏れをチェックして報告する
  • 散らかったファイルの整理案を、週1で提案してもらう

どこで登録するのか

登録する場所が、そのまま「どちらの自動化になるか」を決めます。ここが分かれ目です。

  1. 自分のPCのフォルダを使いたい → デスクトップアプリで登録する

    左のサイドバーの「スケジュール」を開きます。「予定済みタスク」という画面が出るので、右上の「作成」から、指示・使うスキル・実行時刻をまとめて設定します。この場合、実行時刻にPCが起きていてアプリが開いている必要があります。

  2. PCのファイルを使わない → ブラウザのCodex画面で登録する

    ブラウザでCodexを開き、同じようにスケジュールを設定します。こちらはPCを閉じていても動きますが、あなたのPCの中のフォルダは見えません。

※ 最初はデスクトップアプリだけで十分です。フォルダの資料を扱う仕事がほとんどなので、非エンジニアの方はまずこちらから始めてください。

i

いきなり自分で作らなくても大丈夫。「予定済みタスク」の画面には「提案」という欄があり、すぐ使える自動化が並んでいます。たとえば「週次レビュー（毎週金曜16:00・最近の仕事を簡潔な進捗報告にまとめる）」「フォローアップを監視（平日9:00・最近のメールやカレンダーを確認し、対応が必要なものにフラグを付ける）」といったものです。まずはこの提案をひとつ有効にしてみるのが、いちばんラクな入口です。

登録したあとの画面

「予定済みタスク」の一覧には、登録したものが「平日の 8:00 ・ 次回実行 23 時間後」のように表示されます。次にいつ動くのかが一目で分かります。

上部のタブで 「すべて／有効／一時停止中」 を切り替えられます。止めたくなったら、削除しなくても「一時停止」にできる——これは覚えておいてください。おかしな結果が出続けているときに、慌てずに止められます。

時刻は画面の欄で指定しますが、下の例のように指示文の先頭にも【いつ】を書いておくと、あとで自分が見返したときに分かりやすくなります。

自動化の指示文（例）
【いつ】平日の毎朝 9:00

【ゴール】
reports フォルダに前日追加された文書を読み、
その日の朝会で使える要約メモを1枚つくる。

【制約】
・既存のファイルは変更しないでください。
・新規作成は daily/YYYY-MM-DD.md の1ファイルだけ。
・外部への送信はしないでください。

【完了条件】
・当日の日付のファイルができている
・「新着の件数」「要点3つ」「要対応のもの」が書かれている
・対象が0件だった場合は、その旨だけを書いて終了する

最後の1行に注目してください。「何もなかったときにどうするか」を書いておくのが、自動化のコツです。これがないと、Codexは無理に何かを作ろうとします。

深掘り自動化がうまくいかない典型パターン
  • PCがスリープしていた。最頻出です。PCのフォルダを使う自動化なら、実行時刻にPCが起きていてアプリも開いているか確認を。
  • 入力が想定と違った。「ファイルが0件」「形式が違う」など。異常時の動きを指示文に書いておきましょう。
  • 手動で試していなかった。自動化は失敗も自動で繰り返します。1回目の失敗を、毎日繰り返す羽目になります。
  • 結果を見ていなかった。気づいたら2週間ぶんの間違った出力が溜まっていた、というのはよくある話です。

ここだけ覚えて

  • 自動化は「指示＋スキル＋時刻」の3点セット。
  • 自分のPCのファイルを使うなら、アプリ起動が必要。使わないならWeb側で留守中も動きます。
  • 自動化は無人で走るので、その場で承認を求められません。権限は事前に絞る。
  • 手動で1回成功したものだけを自動化する。これは徹底したいルールです。
  • 指示文には「何もなかったときの動き」を必ず書く。
第11章へ：安全に使うコツとつまずき集

Chapter 11

安全に使うコツと、
つまずき集

Codexは、あなたのPCで実際に手を動かします。だからこの章は、読み飛ばしてほしくない章です。とはいえ、覚えることは多くありません。

3行でいうと

  • 承認は「承認を求める」から始める。慣れてから緩める。
  • 取り返しがつかないこと（削除・送信・公開・支払い）は任せない。
  • 「元に戻せる状態」を作っておけば、ほとんどの失敗は怖くない。

🔑 たとえるなら

新しく来た助手に、初日から金庫の鍵と会社のクレジットカードを渡す人はいません。まずは倉庫の見学から。信頼できると分かってから、少しずつ権限を渡していきます。

Codexとの付き合い方も、まったく同じです。相手が優秀かどうかの問題ではなく、手順として正しいかどうかの問題です。

承認のしかたは、2つから選ぶ

設定する場所は、依頼を書く入力欄のすぐ下・左寄り。「承認を依頼」という表示をクリックすると、「ChatGPT のアクションの承認方法」というメニューが開き、次の2つが並んでいます。

既定・こちらを推奨

承認を求める

外部ファイルの編集やインターネットの利用について、常に確認を求めます。

いちいち聞かれるので手間に感じますが、慣れるまではこれが正解です。何を許可したのかが自分で分かります。

慣れてから

代わりに承認

安全でない可能性があると検出された操作についてのみ確認を求めます。

日本語が少し分かりにくいのですが、「あなたの代わりにCodexが判断して承認する」という意味です。確認の回数は減りますが、そのぶん任せる範囲が広がります。

基本方針は、ひとことで言えばこうです。
まずは「承認を求める」。作業に慣れて、内容を予測できるようになってから緩める。

!

「代わりに承認」でも、無制限ではありません。危険と判定された操作では止まります。ただし「何が危険か」を判断するのはCodexであって、あなたの事情までは知りません。「このフォルダだけは絶対に触られたくない」といった事情があるなら、それは依頼文の【制約】に書くのが確実です。

深掘りもっと細かく制限したいとき（サンドボックス）

アプリの選択肢は2つですが、その裏ではサンドボックスという仕組みが働いています。Codexが動き回れる範囲を、あらかじめ囲っておくものです。

CLI（黒い画面から操作する上級者向けの入口）では、この範囲をもっと細かく指定できます。よく使われるのは次の3段階です。

  • 読み取りのみ：見るだけ。何も変わりません
  • 作業フォルダ内だけ書き込み可：実作業の標準
  • 全面的に許可：使い捨ての環境に限定すべき

非エンジニアの方は覚える必要はありませんが、「範囲を囲う」という考え方があることだけ知っておくと、設定画面で「サンドボックス」という語を見かけたときに慌てずに済みます。

任せてはいけないこと

  • 本番環境への反映。本番環境とは、お客さんや社内の人が実際に使っている、いま動いているシステムのこと。ここに確認なしで手を入れさせない。
  • パスワードやAPIキーなどの秘密情報。APIキーとは、外部サービスに接続するためのパスワード相当の長い文字列です。依頼文にそのまま貼らない。ファイルに書いてある場合は、そのファイルを対象から外す。
  • お金が動く操作。購入、契約、送金。
  • 外部への送信・公開。メール送信、SNS投稿、公開設定の変更。
  • 大量削除。「不要なファイルを消して」は、定義があいまいなまま実行されると危険です。

これらは「Codexが信用できないから」ではありません。人間の部下に対しても、同じ線引きをするはずだからです。

安心して使うための、3つの備え

  1. コピーで作業する

    大事なフォルダは、複製してから渡す。いちばん単純で、いちばん確実です。

  2. 履歴の残る仕組みの上でやる

    Git を使っていれば、いつでも前の状態に戻せます。ここが、AIに任せるうえでの最大の安全網です。

  3. 1回の依頼を小さくする

    大きく任せるほど、確認も、やり直しも大変になります。小さく頼んで、こまめに確認する。

つまずき集（よくある質問）

最初の2つだけは、困る前に開いておいてください。残りは、実際に困ったときで大丈夫です。上から順に、遭遇しやすい順に並べています。

Q途中で止めたい。どうすれば？

実行中は停止のボタン（または Esc キーなど）で中断できます。中断しても、それまでの変更は残っていることがあります。止めたあとは必ず差分を確認し、不要な変更があれば戻してください。

「止めていいのか分からない」という状態なら、止めて構いません。中断による損害より、暴走を放置する損害のほうが大きいです。

Q思っていたのと全然違うものができた

まず、あなたのせいではありません。ほとんどの場合、原因は3つのどれかです。

  • 完了条件が書かれていなかった（第3章）
  • 1つのタスクに用件を詰め込みすぎた（第5章）
  • 会話が長くなりすぎていた（第7章）

対処は、新しいタスクで、完了条件を明記して、もう一度頼む。これでかなり改善します。

Q同じ間違いを何度も繰り返す

2回目までは指摘で直します。3回目が来たら、それはスキルにするサインです（第8章）。

「毎回これを注意している」ということは、それがあなたの暗黙のルールだということ。マニュアルに書けば、二度と言わずに済みます。

Q作業が遅い・進まない
  • 渡した範囲が広すぎる。フォルダ全体ではなく、対象ファイルを指定してみてください。
  • 承認待ちで止まっている。画面に確認が出ていないか確認を。
  • そもそも大きすぎる仕事。3つに分けて頼むほうが、結果的に速いことがよくあります。
Q使用量の上限に達してしまった

プランごとの上限があります（第7章）。Plus・Pro ではクレジットを追加購入して継続できます。

その前に見直したいのは使い方です。「渡す量を減らす」「用件ごとにタスクを分ける」だけで、消費量はかなり変わります。

Q会社のファイルを扱っていいのか不安

判断材料は2つあります。

  • ローカル実行なら、ファイルはPCの中で処理されます（ただしAIとのやりとり自体は通信を伴います）。
  • クラウド実行は、コピーを外部に預けることになります。

迷ったら、まず社内のルールを確認してください。「AIツールの利用規程」が整備されている組織が増えています。確認が取れるまでは、練習用の無害なデータで練習するのが賢明です。

QAIの出した答えを、そのまま信じていい？

いいえ。これはCodexに限らず、すべての生成AIに共通する原則です。

AIはもっともらしく間違えることがあります。特に、事実関係・数値・固有名詞は要注意です。

ただしCodexには利点があります。「実際に動かして確かめる」ことができるため、机上の空論で終わりにくいのです。「動くかどうか、実際に試して確認して」と依頼に足すだけで、信頼性は目に見えて上がります。

ここだけ覚えて

  • 承認は「承認を求める」のまま始める。緩めるのは、内容を予測できるようになってから。
  • 削除・送信・公開・支払いは任せない。人間の部下と同じ線引きです。
  • コピーか、履歴が残る場所で作業する。戻せるなら、失敗は失敗になりません。
  • 迷ったら止める。聞き返す。それが上級者のふるまいです。
